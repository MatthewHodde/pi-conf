# Judging: exclude with grounds

Read this when the Close operator fires: candidates need choosing, a recommendation is about to carry meaningful downside, or the evidence behind a choice is disputed.

## Sort the input first

Separate four kinds before comparing anything:

| Kind | Test |
|---|---|
| verified fact | Can the environment, a record, or a direct observation support it? |
| secondhand account | Who said it, and what could they actually observe? |
| inference | What fact is being interpreted, and what other reading also fits? |
| value | What does the user care about, tolerate, or owe? |

Do not promote an inference because it sounds precise. Do not treat a value as a fact research can settle. Say the situation back in these terms before asking for more.

Missing information changes the confidence of the judgment, not whether you give one. Deliver the conditional version and name the missing piece. When several interpretations stay live, state for each the evidence that would distinguish it. If one question can split them cleanly, prefer a binary counterfactual and say what each answer changes. Otherwise offer a small recognition set with a none-fit exit, never open recall.

## Find the real decision

Whether comes before how. A polished implementation cannot answer whether the move deserves to exist. For a product or feature, check:

- demand: a real recurring case, not a feeling that it ought to exist
- supply: whether something on hand already covers it
- mechanism: what the proposed move actually changes
- proof: what result would count as improvement

When the judgment turns on a tolerance or value only the user can supply, name it specifically. "Only you can decide" is useful only when it says what only they know.

## Compare in the same units

1. Fit with the actual goal.
2. Hard constraints.
3. Main downside, and who bears it.
4. Reversibility.
5. Cost of being wrong.
6. Evidence that would reveal the mistake early.

Give the strongest case for each live option before leaning. Do not spend equal words on options that fail a hard constraint. When no direction exists, offer two or three that differ in mechanism. When one exists, examine it rather than replacing it with your taste.

## Deliver

With adequate grounds: the leaning, what it rests on, the condition most likely to overturn it, when the strongest alternative should win, and the first reversible move if action fits.

Without adequate grounds: what can already be concluded, what remains unknown, the single piece of evidence that would move the decision most, and the smallest way to get it.

Either way the user leaves with content, never just a question or advice about how to think.

## Depth

A short request gets one pass: the reading, the leaning, what would change it. Go deeper only when the choice is hard to reverse, carries material downside, or stays uncertain after the first pass. A long-horizon design adds: the feedback that reveals error early, the part that compounds, the cap on the downside, the condition for stopping.

## Boundaries

- Never invent numbers, timelines, circumstances, or tolerances for the user.
- How long or how intensely they have been uncertain shows the issue matters, not what caused it.
- No bias labels as diagnosis. Ask the counterquestion in plain language: not "that's sunk cost", but "starting from today, is the next month of work worth it?"
- A settled delivery request gets handed off, not re-examined.
